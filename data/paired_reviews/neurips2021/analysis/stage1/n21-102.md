**Verdict.** The rebuttal moved Committee B and did not move Committee A. Before it, B stood no higher than A. A's ratings, 7, 4 and 4 (mean 5.0), never changed. Three of B's four reviewers wrote that they raised their scores, so B's pre-rebuttal mean was 5.0 at most. Both committees saw the same faults: an incremental combination of known parts, one task, no error bars, a loss to Code Transformer on JavaScript, and an unexplained absolute-path result. B's movers held objections that new numbers could answer: capacity, depth, JavaScript and error bars. A's two detractors objected to limited significance and lack of insight, which new numbers did not answer. The area chairs (ACs) then read the same new results in opposite ways. The paper is borderline, and the committees weighted the same facts differently. Neither found a fatal flaw.

**Committee A (reject).** Ratings 7, 4, 4. Reviewer_FGbv's 7 is specific and engaged, but FGbv wrote that it did not know "whether the comparisons are fair". Reviewer_SWC5 (8 hours) called TPTrans "a novel combination of existing architecture components" of limited significance. Reviewer_43xz listed modest gains, one task, arbitrary placement of the path terms and little insight. Table 2 bears out the gains: 1.5 to 2.7 F1 over Code Transformer on Python, Ruby and Go, and 1.2 below it on JavaScript. SWC5 thanked the authors for parameter counts and error bars and kept 4. 43xz never replied. The AC's concerns follow 43xz's list of cons. The AC added its own reading of the late code-classification results: "not clear if TPTrans performs better than stronger baselines". The authors' table confirms it: 94.94 on POJ-104, against 95.21 (TBCNN), 98.2 (ASTNN) and 98.32 (TreeCaps).

**Committee B (poster).** Ratings 4, 6, 7, 6. Reviewer_5kuu kept 4 on novelty and on the overbroad "first ones" claim (lines 76-77), which the authors conceded. But 5kuu's statement that TPTrans differs from Code Transformer only by using a CST is wrong. TPTrans encodes each path's node sequence, and Table 4 shows that reducing paths to hop counts costs 0.9 to 2.5 F1. Reviewer_y3EX (confidence 5) based its "primary concern" on a wrong assumption. The paper's settings (lines 250-254) imply about 50K added GRU parameters, and the authors put the model at about 100M. y3EX then asked for a deeper, narrower Transformer, and only B got the answer: on Ruby, 24.97 F1 for TPTrans against 20.23 for a plain Transformer. Reviewer_ZRpb raised its score on JavaScript path statistics that the authors themselves called inconclusive. Reviewer_86qv credited the whole set of new experiments. The AC conceded that the idea is "closely related to multiple recent efforts", called the new results "compelling", and followed the majority.

**Issues one committee raised and the other did not.** Only A asked why the path terms enter Key and Value but not Query (Reviewer_43xz). Only A flagged Section 3 text that resembles Zügner et al. (Reviewer_SWC5). The ethics reviewers found no ethical issue, and the AC did not mention it. Only A noted a missing citation of Alon et al. 2020 (Reviewer_FGbv). Only B noted that the Code Transformer paper reports better multilingual results than the monolingual numbers in Table 2 (Reviewer_ZRpb). The authors did not dispute this, and no reviewer pursued it. Only B challenged the three-layer, 1024-wide set-up as unfair to deeper baselines (Reviewer_y3EX). The test that answered it compares TPTrans with a plain Transformer, not with Code Transformer.
